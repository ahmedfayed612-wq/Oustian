Part A · Summary (5-minute read)

In plain English

Oustians is a private social app built for OUST students — a campus feed with photos, short-lived stories, study groups, messaging, events and notifications, in both English and Arabic. The app is built end to end and its core features (posting, reactions, stories, groups, chat) are wired through the app, the server logic and the database. This report comes from reading the code only: the live servers, web address and email delivery were not tested. A short list of known gaps — upload safety checks, automatic cleanup, automatic checks on every code change, and a backup drill — should be closed before a wider launch.

At a glance

11 features fully built

70 / 70 unit tests passing
Reactions, media, stories, group size, roles, suggestions

Avatar upload check, story cleanup job, automated checks (CI), backup drill

What was not checked

  • Live database access rules, file storage and login settings
  • oustians.com web address and security certificate

  • Login email templates and delivery
  • Trial run of all 16 database updates on a test copy
  • Behaviour under load (group-size and connection races)

Overall assessment

The codebase is a coherent, carefully structured campus app: strict typed code, database-level access rules on every table, and green unit tests over the riskiest interactive cores (reactions, stories, group size). Against that stand concrete pre-launch gaps — the avatar file check, story cleanup automation, automatic checks on every change, and a proven backup restore — plus live-system verification that has not happened yet. Close the four must-fix items, verify the live environment, and the app is in a defensible position for a staged wider launch; it is not claimed secure or production-ready today.

Part B · Technical detail

What this means: the short version for decision-makers — what the app is, how it is put together, and what still needs attention.

Oustians is a private invite-gated campus social app for OUST students: feed, stories, presentation groups, connections, chat, events, notifications, admin moderation. Frontend Next.js 16 App Router (RSC + client islands) under src/app/[locale]/. Backend is Supabase-only: Auth, Postgres + RLS (Row-Level Security: database rules that decide who may see or change each row, ~62 policies), ~40 RPC functions (Remote Procedure Calls: named database routines the app invokes), 3 Storage buckets, Realtime for chat. No custom REST server, queue, cron, search or payment service exists in code. Mutation convention: Server Action (a function that runs on the server when a student taps a button) -> Zod (a data-shape checker) -> requireApprovedMember/requireAdmin -> RPC or RLS query.

Strengths
Coherent Supabase-native design, strict TS, RLS-first, 70/70 unit tests green, clean brand tokens in src/app/globals.css.
Launch blockers (P0)
Avatar ticket lacks byte-sniff; no story purge schedule; no CI/SAST; backup/restore unproven.
Scale notes
Member search is ilike full-scan; no post search; write-path rate limits partial; N+1 risk (fetching a list then re-querying per item, which multiplies database trips) in rings/cards.
Verification limit
Static audit only. Live Supabase, Vercel env, DNS/TLS and Auth email were not accessed - UNVERIFIED.

Glossary (plain language)

TermWhat it is
RLS (Row-Level Security)Database rules deciding who may see or change each row.
RPC (Remote Procedure Call)A named routine stored in the database that the app calls.
Server ActionA function running on the server when a student taps a button or submits a form.
Magic-byte sniffReading a file's first bytes to confirm its real type (image vs disguised file).
FTS (Full-Text Search)A database index that makes text search fast; absent here, so search scans row by row.
N+1Fetching a list then querying once per item — multiplies database trips.
CSP (Content-Security-Policy)A browser header whitelisting allowed content sources.
SASTAutomated static scan of code for security flaws.
CI (Continuous Integration)Automatic type/style/test checks on every proposed code change.
RSCReact Server Component: page parts rendered on the server before reaching the browser.
PITRPoint-in-time recovery: restoring the database to an earlier moment.
